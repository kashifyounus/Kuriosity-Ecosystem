## 1. Publication Decision

KEP Framework v1.0.0 is the first official, product-adoptable KEP governance baseline.

This release publishes the already approved constitutional and subordinate governance instruments identified in the authoritative release manifest. It does not create a new governance domain, alter an approved normative clause, resolve a deferred decision, or authorize implementation capabilities outside the approved baseline.

## 2. Authoritative Release Identity

The contractual adoption identifier is **KEP Framework v1.0.0**.

The repository-controlled release declaration and manifest on the authoritative branch establish the release. A Git commit records implementation evidence but is not the contractual adoption identifier. A Git tag or GitHub Release may mirror this release for distribution convenience but is not required for validity or adoption.

## 3. Release Contents

The complete release contents, document versions, lifecycle states, canonical paths, and supporting evidence are defined only by:

`docs/00-governance/releases/KEP-v1.0.0-release-manifest.md`

No product or operator may infer additional release contents from repository proximity, conversation history, branch history, an unversioned reference to `main`, or an optional distribution object.

## 4. Product Adoption

A product repository deterministically adopts this release by recording:

1. The canonical KEP repository.
2. The adopted framework version: `v1.0.0`.
3. The authoritative manifest path.
4. The adopted standards and versions selected from that manifest.
5. Product-specific extensions and approved deviations.
6. Its controlled upgrade and rollback policy.

A product is not required to adopt every future KEP release. Adoption remains pinned to `v1.0.0` until the product approves an upgrade.

## 5. Release Boundaries

This release does not:

- Change applicable law or binding contractual precedence.
- Transfer product-domain ownership to KEP.
- Authorize product implementation.
- Resolve deferred decisions preserved by the included standards.
- Make a Git tag or GitHub Release authoritative.
- Include draft, reserved, superseded, or unapproved standards.

## 6. Optional Post-Publication Distribution

The following activities are optional and non-blocking:

- Create a Git tag named `v1.0.0`.
- Create a GitHub Release associated with that tag.
- Attach rendered or packaged release copies.

If created, those objects shall reference this declaration and manifest and shall not redefine release contents.
